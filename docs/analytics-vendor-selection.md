# Analytics Vendor Selection

This document captures the decision framework for selecting a third-party
analytics provider behind [`AnalyticsTracker`][analytics-tracker] and
the vendor-neutral adapter that will live in `androidMain` / `iosMain`.

It is the vendor-selection slice of [#180][issue-180] (V1 production
analytics). It is intentionally a framework, not a contract — when the
team picks a vendor the chosen provider is recorded in
[Implementing section](#implementing).

## Constraints

The provider must satisfy every constraint below. If a vendor fails
any of them it is disqualified, regardless of feature breadth.

| Constraint | Source |
| --- | --- |
| Vendor SDK ships only with opt-in initialization, never implicit auto-start. | [`docs/privacy.md`][privacy], [Issue #62][issue-62] |
| Vendor SDK allows a custom allowlist of properties attached to each event. | Privacy contract |
| Vendor SDK does not collect identifiers we have not linked. | Privacy contract |
| Vendor SDK supports on-device aggregation or scrubber before egress. | Privacy contract |
| Vendor SDK supports anonymous install identity that we generate. | Anonymous identity policy |
| Vendor SDK supports regional data residency that we can pin to JP for the V1 launch. | Store listing |
| Vendor SDK license is compatible with our binary distribution. | Compliance |
| Vendor SDK first-party dependency footprint is small. | [`docs/dependency-policy.md`][dep-policy] |
| Vendor SDK is actively maintained (release within last 6 months). | Abandoned-dependency signal |

## Provider landscape (V1 candidate set)

The team should evaluate these candidates against the constraint table
above. The list is not exhaustive; new candidates must satisfy the
constraints before being added.

| Candidate | Strengths | Open concerns |
| --- | --- | --- |
| Firebase Analytics (`firebase-analytics` / `FirebaseAnalytics`) | Mature, free tier covers V1, integrates with Crashlytics. | Default payload includes IDFA-like signals unless explicitly disabled. Privacy policy must match. |
| Mixpanel (`mixpanel-android` / `mixpanel-swift`) | Strong funnels and retention dashboards. | Default identity policy is more invasive than the V1 privacy contract allows. |
| Amplitude (`amplitude-android` / `amplitude-ios-swift`) | Strong product analytics, EU residency option. | Cost scales with MAU; need to validate V1 cost projection. |
| PostHog (`posthog-android` / `posthog-ios`) | Self-host option, BYO pipeline, generous free tier. | Smaller SDK maturity; verify on-device scrubbing. |
| Plausible / Umami (self-host only) | No third-party data sharing. | No first-party mobile SDK; requires building our own HTTP adapter. |

Each candidate must also be reviewed against the [abandoned-dependency
signal](dep-policy.md#abandoned-dependency-signal) and the
[cold-start dependency cap](performance-budget.md#cold-start-dependency-cap)
before adoption.

## Implementing

Once the team selects a vendor, the implementation slice is:

1. **Vendor SDK adapter** in `androidMain` / `iosMain`.
   The adapter implements [`AnalyticsTracker`][analytics-tracker] and
   delegates `track(event)` to the vendor SDK after scrubbing.
2. **Wire in `MainActivity`** (Android) and `MainViewController`
   (iOS) by constructing `BedtimeAnalytics` from the platform store,
   the vendor adapter, and passing it to `SoineApp`.
3. **Scrubber** that drops any payload field the vendor SDK tries to
   attach that is not on our allowlist (see
   [`docs/privacy.md`][privacy]).
4. **Provider configuration** lives in BuildConfig / xcconfig so the
   SDK key is not committed. Provider SDK keys are GitHub / Store
   secrets ([`docs/security-audit-2026-10.md`][security-audit]).
5. **Debug build verification** runs `:androidApp:assembleDebug` with a
   fake `installId` and asserts the events appear in the vendor
   dashboard.
7. **Release build verification** confirms the vendor SDK is
   initialized (not `NoOpAnalyticsTracker`) and that the dashboard
   receives events.
8. **Privacy policy update** is filed as a follow-up issue and is
   blocking the V1 store submission per
   [`#181`][issue-181].

## Anonymous identity policy

The install id is generated by [`AnalyticsIdentity`][analytics-identity].
It is a 128-bit cryptographically random value persisted via
[`AnalyticsPreferencesStore`][analytics-prefs]. It is **never**
derived from:

- hardware identifiers (ANDROID_ID, advertising ID, IDFV, MAC, IMEI),
- account identifiers,
- device serial numbers,
- email / phone / name.

It is regenerated when the user clears local data
([`LocalDataDeletionService`][local-deletion]). It is not rotated on
every app launch.

## Opt-out

The `enabled` flag in [`AnalyticsPreferences`][analytics-prefs] defaults
to `false`. The Settings screen surfaces a toggle that flips the flag.
When the flag is `false`, `BedtimeAnalytics` is a no-op and the
vendor SDK is never initialized (no network traffic, no device
registration).

## Acceptance criteria

- V1 funnel (`start → completion`, `morning summary open`,
  `D1/D7/D30 return-to-bedtime`, `nights completed per active user`,
  `renderer fallback rate`, `session recovery rate`) is visible in a
  dashboard.
- No privacy-sensitive payload reaches the vendor SDK.
- The vendor SDK is never initialized while `enabled == false`.
- Vendor SDK failure (offline / 5xx) does not break the sleep flow.
